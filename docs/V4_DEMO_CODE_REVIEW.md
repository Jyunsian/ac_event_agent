# V4 demo 與正式程式對照 review

後續：使用者已授權修復；最新實作與驗證另見 [V4-REVIEW-FIXES](../evidence/V4-REVIEW-FIXES.md)。以下保留發現時的紀錄。

日期：2026-09-17。這輪只做程式檢查與小案例驗證，未修改產品程式，不更新既有階段驗收狀態。

結論：三群、六個觀察時間與五個判斷面向已有正式計算與 Web 呈現，但 demo 不能代表正式介面已完整落地。除了合理的示意數字差異，還有時間判斷錯誤與跨介面缺口。

## 優先處理的問題

### 1. P1：後來的缺失收入會抹掉之前已確認的達標

位置：`server/analysis/v4_features.py:31–40、185–190、273–276`。

滾動收入判斷會先檢查整段資料，只要任意事件的收入或可用時間缺失，就把玩家改成未知。手算案例：第一小時已有可靠收入 2 元，門檻 1 元，在 24 小時應已達標；加入第 72 小時的一筆缺失收入後，24 小時結果變成未知。字典與陣列路徑都重現。

累積收入也有相似問題：後面的事件缺少收入可用時間，會把完整時間線改成從第 0 秒起未知，丟掉先前可靠的達標證據。

影響：前一天人數、首次達標、每天新增及後續驗證都可能受影響。修正應依當時可取得資料判斷，保留已可靠確認的首次達標；未知資料不能反向改寫過去。證據：`.runtime/v4-review/time-boundary.json`、`.runtime/v4-review/edge-cases.json`。

### 2. P2：demo 的第一天滾動與累積人數互相矛盾

位置：`web/public/mock-v4.html:18–19`。

demo 顯示「累積完成 10 關」24 小時有 1,800 人，「連續 24 小時完成 10 關」有 1,500 人。按本版定義，滾動要等完整 24 小時才開始判斷；第一次判斷時，兩者查看的是同一段事件。在相同資料、門檻及邊界下，人群應相同。觸發速度可以不同：累積條件可在第一小時觸發，滾動需等到 24 小時。

正式 fixture 的同門檻廣告次數比較得到 16 對 16，玩家身分相同。之後的觀察時間才可能出現滾動人群較小。這是示例邏輯錯誤，不能只用「數字是 mock」解釋。

### 3. P2：第一天不能判斷的條件，仍被算成「比第一天多找到」

位置：`server/analysis/v4_metrics.py:40–57`。

`added_since_24h` 一律使用目前達標者減去 24 小時達標者。若回訪條件在 24 小時尚不能判斷，第一天集合為空，48 小時達標的所有玩家就被寫成額外找到。

小案例已重現：24 小時 `applicable=false`，48 小時卻顯示多找到 1 人。此時應顯示「此條件不適用 24 小時比較」，不能把無法判斷當成沒找到。證據：`.runtime/v4-review/edge-cases.json`。

### 4. P2：正式頁面缺少 demo 的圖表，外層頁籤未接入 V4

位置：`web/src/report-v4.tsx`、`web/src/report-panel.tsx:49`。

demo 有六天堆疊柱狀圖與摘要卡，正式 V4 主要為表格，沒有對應的柱狀圖。ReportPanel 遇到 V4 直接回傳 ReportV4，未傳入外層 tab；切換外層概覽、候選、圖表與資料品質不會切成各自的 V4 內容。

正式每日新增表格也未完整展示已計算的新增人群總收入及占全體收入比例。不能把「產物中有數字」當成「客戶介面已看得到」。

### 5. P2：Web 有三群，Agent 仍只收到其中兩群

位置：`server/analysis/v4_metrics.py:87–104`、`server/read_tools.py`、`web/src/chat-panel.tsx:76`。

正式驗證產物與 Web 已有全量、找規律及 holdout。Agent 的聚合投影仍只選 observation 與 holdout，缺少各規則的 exploration 數字。聊天請求也沒有帶目前選中的時間及人群；只問「這群怎麼樣」時，Agent 不能可靠知道畫面所指對象。

demo 的問答是預設內容，不能視為正式 Agent 已能解釋三群的驗證。需同步工具讀取與聊天的選取上下文。

### 6. P2：離線 HTML 的三群呈現尚未補齊

位置：`server/analysis/v4_report.py:84–92`。

離線 HTML 已有三群每日表格，但收入對照的格式化表格仍只列全量與 holdout；滾動對累積的格式化比較只顯示全量。CSV／JSON 保有對應原始聚合資料，問題在呈現契約不一致，並非所有匯出數字都不存在。

### 7. P3：第一天顯示「比第一天多找到 +0」仍然容易誤解

demo 與正式表格都有此語意。算術正確，但應在 24 小時顯示「第一天：比較基準」，從 48 小時起才顯示「比第一天多找到」。之前討論的文字改善尚未完整落地。

## 合理但必須說清楚的差異

| 項目 | demo | 正式程式 |
|---|---|---|
| 行為數 | 固定三條 | 搜尋結果；優先展示最多十條，完整清單分頁讀取 |
| 三群人數 | 10,000／7,000／3,000 | 按安裝日期切分，不保證正好 70／30；資料不足可能無 holdout |
| 收入、等待時間 | 手寫數字、比例推算 | 各群依實際事件與首次達標時間計算 |
| 收入比較的區間與證據狀態 | 示意區間、固定文案 | 依樣本、重抽樣及多重比較校正判斷 |
| 缺失資料 | 示意資料基本沒有未知 | 正式保留未知；覆蓋比例分母為可判定玩家 |
| 對話 | 預設問答 | Agent 與分析工具，仍有上述三群資訊缺口 |

已確認成熟用戶的定義是可觀察至安裝後 168 小時，不是每天都要登入。用戶表 LEFT JOIN 事件，能保留名冊內的零事件玩家；若來源資料根本沒有這位下載者，系統不能憑空補入。缺失收益與未滿七天不能當成零收益。
