# Goal：完成 Candidate Event V2 算法與客戶證據報告

## 一句話目標
讓內部 IAA 分析人員上傳既有事件級 CSV 後，能向客戶交付可追溯的全部候選結果與少數具不同價值／覆蓋／速度優勢的比較選項，並用白話證據卡判斷下一步投放測試的取捨。

## 為什麼是現在
- 現行搜尋窗口與收入網格偏粗，僅按探索收益差額選最多 10 個驗證；客戶無法取得全部候選的完整證據，UI 多項指標藏在 JSON。

## 目前狀態 → 目標狀態
- Before：已有本地持久 Python/Agent/匯出管線，V2 尚未實作；歷史 gate 不等於新版驗收。
- After：新窗口與累積收入搜尋、整批凍結驗證、來源與剩餘收益診斷、優先/完整清單、完整證據卡及三格式交付實際連通且可恢復。

## 第一版範圍
- 包含：完整依 docs/CANDIDATE_V2_PLAN.md CV01–CV05 與逐項 criteria 執行。
- 不包含：滾動窗口（僅 AGENTS.md 待辦）、任意產品事件、成本上傳、ROI 保證、SDK 回傳或雲端部署。

## 成功指標
- 全部實際評估候選均有可定位的結果/不足原因；優先比較最多 10 個、不湊數，完整客戶清單不被精選名單截斷。
- 同一輸入/配置/版本/seed 可重現，所有展示及匯出數字可追溯，既有報告保持不變。
- 新版通過 10萬/100萬事件及 2,000 候選容量情境、端到端與必要回歸，留存可檢查證據。

## 驗收標準
- [ ] CV01–CV05 全部 C1–C3 及 G1–G5 逐階段 passed，evidence/CVxx.md 與 PHASE_STATUS.md 同步。
- [ ] 窗口、收入/頻次/時間/Session/組合/序列搜尋、預算與剪枝和批准計畫一致。
- [ ] 全部候選凍結後驗證、多重比較及時間切分防洩漏通過；D6 不因剩餘時間短被淘汰。
- [ ] 完整清單、證據卡、source/逐日/收益分解與三格式交付一致；客戶可查看不支持及樣本不足項。
- [ ] 真持久背景計算/恢复、Agent 引用、舊版相容、桌面/手機/離線匯出與容量有實跑證據。
- [ ] 交付修改檔案、實際命令、退出碼、產物位置、容量限制及外部待驗事項，沒有未收取的執行結果。

## 限制與依賴
- 遵守 AGENTS.md；保留原始檔、父報告、已完成歷史證據與使用者工作。分析使用 DuckDB/Parquet、真 PG/S3 與既有 Worker 架構。
- 不依賴真客戶資料/付費模型完成可本地驗證部分。新 SDK/套件查官方資料並鎖版。未部署不得稱上線。
- 已授權本範圍，自動跨阶段繼續，不反覆詢問開始；核心錯誤與容量失敗先修復，不能當外部延期或降低驗收。

## 已確認事實
- 用戶表每人一列、事件表每事件一列；逐次廣告收益由 Python 累加。全來源合併且時間切分，D7 主目標不變。
- 使用者確認完整客戶清單、擴充到 D6 的固定起點窗口，以及累積收入作主要搜尋方向。

## 關鍵假設
- 離線歷史辨識有助於選擇投放測試 signal；它不證明平台可買到相同人群或達成 ROI。
- Welch 的近似、2,000 候選下的計算成本需透過指定統計/容量測試檢查，不以設計宣稱通過。
